# VaultKey — état du projet et direction retenue

Référence produit, modèle de données et sécurité : `PRD-vaultkey-web-v3.md`. Ce PRD remplace intégralement l'ancienne architecture native macOS (FSKit, puis FUSE-T, PIV/CryptoTokenKit) : voir sa section 1 pour l'historique des architectures rejetées, pas la peine de le répéter ici. Tout le code et les notes liés à cette ancienne architecture ont été supprimés du projet (spikes FSKit et CryptoTokenKit, FUSE-T, YubiKey Manager, ancien PRD v2, ancienne maquette native) : ne pas y faire référence, ne pas repartir de ces approches sans que l'utilisateur ne relance le sujet lui-même.

Architecture retenue, en une phrase : application web servie par un conteneur Docker auto-hébergé, cœur de chiffrement Rust compilé en WASM exécuté dans le navigateur, déverrouillage par YubiKey via l'extension PRF de WebAuthn, serveur strictement aveugle (ne stocke que des blobs chiffrés).

## État de l'environnement de développement (cette machine)

- macOS 26.6.2 (build 25G83).
- `cargo`/`rustc` 1.98 disponibles (`~/.cargo/bin`).
- Docker Desktop 4.88 installé et lancé le 2026-08-25 (`brew install --cask docker-desktop`), `docker compose` v5.4 disponible.
- `wasm-pack` 0.15 et la cible `wasm32-unknown-unknown` installés le 2026-08-25 (`rustup target add` + `cargo install wasm-pack`, aucun sudo).
- Node.js 24 disponible, utile pour des smoke tests rapides du module WASM hors navigateur (voir étape 2 ci-dessous) — ne remplace pas une vérification dans un vrai navigateur.
- Navigateur de test recommandé par le PRD (section 3) : Firefox 148+ en premier choix. Safari déconseillé pour l'instant (bugs WebKit ouverts affectant PRF avec des clés de sécurité USB/NFC externes) — à re-vérifier périodiquement, pas une limite figée.
- Aucun outil résiduel de l'ancienne architecture native sur cette machine (Xcode, FUSE-T, YubiKey Manager, pkgconf ont été désinstallés le 2026-08-25).

## Exigences de sécurité non négociables (section 7 du PRD, à ne jamais relâcher pour la commodité de l'implémentation)

- Clé maîtresse du coffre : exclusivement `crypto.getRandomValues` (WebCrypto), 256 bits pleins, jamais dérivée d'un mot de passe ni d'une saisie utilisateur.
- Nonce AES-GCM frais à chaque chiffrement de fichier, jamais réutilisé dans un même coffre : prévoir un test explicite qui le vérifie (voir critères d'acceptation du PRD).
- Cœur Rust : aucune dépendance réseau (pas de HTTP, pas de socket), vérifiable au niveau du `Cargo.toml`.
- Clé maîtresse déballée : mémoire uniquement, jamais persistée en clair, effacée explicitement au verrouillage.
- Serveur : zero-knowledge strict, aucune logique de déchiffrement à aucun endroit du code serveur.

## Ordre de travail

Suivre l'ordre de développement de la section 9 du PRD (`PRD-vaultkey-web-v3.md`), sans le dupliquer ici pour éviter que les deux divergent.

**Étape 1 (cœur Rust) : faite.** Crate `core/` (package `vaultkey-core`), `cargo test` passe (17 tests), `cargo clippy --all-targets -- -D warnings` propre, aucune dépendance réseau dans l'arbre complet (vérifié via `cargo tree`). Décisions de conception prises pendant l'implémentation, à ne pas rediscuter sans raison nouvelle :
- `wrappedMasterKey` (enveloppes ET `manifest.enc`) : blob opaque base64 `nonce(12o) ∥ ciphertext ∥ tag`, un seul champ, packé/dépacké par `aead::pack`/`unpack`.
- **Exception** : les blobs de fichier (`<blob-id>.enc`) ne suivent PAS ce pattern. Le nonce de chaque fichier est stocké séparément dans l'entrée de manifeste (`FileEntry.nonce`, PRD §5.2), le blob sur disque ne contient que ciphertext+tag. Différence volontaire : le manifeste a un endroit pour stocker ce nonce, `manifest.enc` lui-même n'en a pas.
- Recovery BIP39 : clé de wrap dérivée via HKDF-SHA256 sur l'entropie brute des 24 mots (contexte fixe `vaultkey-recovery-wrap-v1`), pas de PBKDF2 façon BIP39 standard.
- Anti-réutilisation de nonce : `NonceTracker` (CSPRNG + `HashSet` en mémoire par session de `Vault`), testé sur 2000 fichiers.
- `rand` 0.10 a renommé `OsRng` en `SysRng` (module `rand::rngs`), et ce type n'implémente que `TryRng`/`TryCryptoRng` (fallible), pas `Rng` : utiliser `SysRng.try_fill_bytes(&mut buf)`, pas `.fill()`. À ne pas re-découvrir si une dépendance future retouche à la génération aléatoire.
- Le crate ne fait aucune I/O disque lui-même (pas de notion de `/data/vaults/...`) : il produit/consomme des `Vec<u8>`, l'écriture sur disque selon la structure PRD §5.1 est la responsabilité de l'appelant (CLI de test, puis serveur Docker à l'étape 4).

**Étape 2 (compilation WASM) : faite.** Crate `wasm/` (package `vaultkey-wasm`, `crate-type = ["cdylib"]`), dépend de `core/` en path. Une seule fonction exportée pour l'instant, `demo_roundtrip(plaintext) -> String` : fait tourner un aller-retour complet (créer un coffre, enveloppe YubiKey de test, chiffrer un fichier, exporter le manifeste, verrouiller, rouvrir, déchiffrer) à l'intérieur du moteur WASM. Le binding complet du `Vault` (une fonction par méthode) est volontairement repoussé à l'étape 3, une fois connu le vrai besoin de l'UI WebAuthn. Page de test minimale : `wasm/www/index.html`, charge `../pkg/vaultkey_wasm.js` (généré par `wasm-pack build --target web` depuis `wasm/`), doit être servie via un serveur statique (`python3 -m http.server` depuis `wasm/`, pas `file://` : le navigateur bloque le `fetch()` du `.wasm` sinon). Vérifié une première fois via un script Node.js (`initSync` + appel direct), puis confirmé le 2026-08-25 par l'utilisateur dans un vrai navigateur via cette page servie en HTTP : round-trip identique, pipeline WASM fonctionnel de bout en bout.

Deux pièges de portabilité wasm32 rencontrés en cours de route, à ne pas re-découvrir :
- `getrandom` (dépendance transitive de `rand`/`uuid`/`aes-gcm` via `core/`) n'a aucune source d'aléatoire par défaut sur `wasm32-unknown-unknown` (pas d'OS). Il faut activer sa feature `wasm_js` (backend `Crypto.getRandomValues` du navigateur) — mais **uniquement dans `wasm/Cargo.toml`** (le crate final cdylib), jamais dans `core/Cargo.toml` : la doc de `getrandom` déconseille explicitement d'activer `wasm_js` dans une bibliothèque, ça casse les builds wasm non-web pour qui réutiliserait `core/` ailleurs. Même chose pour `uuid`, qui a besoin qu'on lui désigne explicitement `rng-getrandom` sur wasm32 (branché sur ce même backend `getrandom`, pas sa propre feature `js` séparée).
- `std::time::SystemTime::now()` panique purement et simplement sur `wasm32-unknown-unknown` ("time not implemented on this platform") : pas d'horloge sans JS. Remplacé dans `core/src/vault.rs` par la crate `web-time` (`web_time::SystemTime`/`UNIX_EPOCH`), qui re-exporte `std::time` tel quel sur cible native et bascule sur `Date.now()` du navigateur sur wasm32, sans aucune condition `cfg` à écrire dans `core/`. Contrairement au point précédent, celui-ci va bien dans `core/Cargo.toml` (pas dans `wasm/`) : `web-time` ne pollue pas les builds natifs, elle ne fait qu'un `pub use std::time::*` dans ce cas.
- Pour déboguer un panic wasm qui remonte juste comme `RuntimeError: unreachable` sans message : ajouter `console_error_panic_hook::set_once()` dans une fonction `#[wasm_bindgen(start)]` (déjà fait dans `wasm/src/lib.rs`, restera utile pour la suite).

**Étape 3 (WebAuthn + PRF), partie JS pure : faite et validée sur la vraie YubiKey de dev le 2026-08-25.** Spike isolé `spikes/webauthn-prf-spike/index.html` (JS pur, aucun WASM, méthode volontairement séquentielle : confirmer PRF avant d'ajouter la complexité WASM par-dessus). Résultats empiriques confirmés :
- L'extension PRF est bien annoncée supportée (`prf.enabled: true`) par cette YubiKey.
- Le secret dérivé fait 32 octets — correspond exactement à ce qu'attendent déjà les fonctions `wrap_master_key`/`unwrap_master_key` de `core/` (`&[u8; 32]`), aucune adaptation de taille nécessaire.
- Deux sels différents donnent deux secrets différents ; le même sel redonne systématiquement le même secret (déterminisme confirmé). Les deux hypothèses fondamentales du PRD §5.3 et §7.C tiennent empiriquement, pas seulement sur le papier.

Deux obstacles rencontrés avant d'obtenir ce résultat, à ne pas re-découvrir :
- **L'extension Bitwarden interceptait l'appel WebAuthn** (`navigator.credentials.create/get`) pour proposer sa propre gestion de passkeys, et a fait échouer la cérémonie avec un `NotAllowedError` générique avant même d'atteindre le vrai sélecteur d'authentificateur du système. Il a fallu désactiver l'extension (`about:addons` dans Zen) pour le test. À garder en tête pour l'UI finale : prévenir l'utilisateur que les gestionnaires de mots de passe/passkeys peuvent interférer avec le déverrouillage YubiKey de VaultKey.
- **Cette YubiKey n'avait jamais eu de PIN FIDO2 défini** (seul le PIN PIV existait, d'un tout autre applet, issu de l'ancien spike CryptoTokenKit maintenant supprimé). Sans PIN FIDO2, la cérémonie restait bloquée indéfiniment sur "en attente du contact" sans la moindre invite visible (Zen ne surface pas de message explicite du genre "définis d'abord un PIN"). Correction à mon nettoyage précédent : j'avais supprimé `ykman` en le jugeant "inutile pour WebAuthn/FIDO2" — c'était faux, `ykman` gère aussi l'applet FIDO2 (`ykman fido access change-pin`), pas seulement PIV. Résolu ici via le panneau macOS natif "Protection PIN FIDO" plutôt que la CLI. À prévoir dans le flux d'onboarding V1 : détecter ce cas et guider l'utilisateur, plutôt que de le laisser face à un blocage silencieux comme celui-ci.

**Étape 3, partie WASM : faite et validée le 2026-08-25.** `demo_roundtrip` (`wasm/src/lib.rs`) prend désormais `wrap_key: &[u8]` en paramètre au lieu d'une valeur fixe codée en dur, avec validation de longueur (32 octets exactement, erreur JS explicite sinon). `spikes/webauthn-prf-spike/index.html` importe `wasm/pkg/vaultkey_wasm.js` (chemin relatif `../../wasm/pkg/...`, nécessite de servir tout le dépôt depuis une seule origine, ex. `python3 -m http.server` lancé depuis la racine du projet, pas depuis `wasm/` ni `spikes/...` séparément) et ajoute une section 3 qui réutilise le secret PRF déjà dérivé en mémoire (pas de nouveau contact avec la clé) pour appeler `demo_roundtrip`. Résultat confirmé par l'utilisateur sur la vraie YubiKey : round-trip identique. **L'étape 3 du PRD §9 est donc entièrement close** : cérémonie WebAuthn faite, secret PRF dérivé, utilisé pour envelopper/déballer une clé de test, dans le vrai cœur Rust compilé en WASM, pas dans une simulation.

**Étape 4 (serveur Docker minimal) : faite et validée le 2026-08-25.** Crate `server/` (package `vaultkey-server`, binaire, Rust + axum 0.8), **ne dépend pas de `core/`** : signal architectural volontaire, le serveur n'a même pas le code pour comprendre/déchiffrer ce qu'il stocke, pas juste une politique qu'on pourrait contourner. `cargo test` passe (4 tests, validation d'ID/anti-traversée), clippy propre.

Décisions de conception prises, à ne pas rediscuter sans raison nouvelle :
- Emplacement des enveloppes de clé, non précisé par l'arbre du PRD §5.1 : `/data/vaults/<vault-id>/envelopes.json`, traité par le serveur comme un blob JSON opaque, sans différence avec `manifest.enc`.
- Endpoints : `PUT`/`GET` sur `/vaults/{vault_id}/manifest`, `/vaults/{vault_id}/envelopes`, `/vaults/{vault_id}/blobs/{blob_id}` — axum 0.8 utilise la syntaxe `{param}`, pas `:param` (changement de syntaxe par rapport aux versions antérieures d'axum, à ne pas re-découvrir).
- `vault_id`/`blob_id` validés côté serveur contre `^[a-zA-Z0-9-]{1,64}$` avant toute construction de chemin (`server/src/storage.rs`) — testé explicitement contre la traversée de répertoire (`../../etc/passwd` etc.), confirmé aussi en conditions réelles via `curl` contre le conteneur (400, jamais d'accès hors `/data`).
- Jeton d'accès (`server/src/auth.rs`) : généré une seule fois si `DATA_DIR/access_token` n'existe pas encore (32 octets aléatoires, base64url), écrit sur disque, affiché une seule fois dans les logs. Rechargé silencieusement aux démarrages suivants, jamais régénéré ni réaffiché — confirmé par un cycle `docker compose down`/`up` réel : même jeton, pas de réaffichage dans les logs, données du volume nommé toujours présentes. Comparaison en temps constant (crate `subtle`), pas une comparaison de `String` naïve.
- Image runtime `debian:bookworm-slim`, pas distroless (plus simple à déboguer via `docker exec` pendant le développement ; la minimisation d'image relève explicitement de la passe de durcissement du PRD §10, pas de maintenant). Pas de TLS géré par ce serveur : le PRD §7.A attend un reverse proxy/VPN en amont pour ça.
- `docker-compose.yml` à la racine du repo (pas dans `server/`) : un seul service, volume nommé `vaultkey-data` monté sur `/data`, port `8080:8080`.

Vérifié en conditions quasi réelles (pas juste `cargo test`) : `docker compose up --build`, jeton lu dans les logs, PUT/GET manifeste et blob avec le bon jeton (200), sans jeton et avec un mauvais jeton (401), manifeste inexistant (404), tentatives de traversée de chemin dans `vault_id` et `blob_id` (400), redémarrage complet du conteneur avec persistance du jeton et des données.

**Étape 5 (flux complet sur un coffre codé en dur) : faite et validée le 2026-08-25, sur la vraie YubiKey, le vrai serveur Docker, le vrai WASM.** `core/`, `wasm/` et `server/` branchés ensemble pour la première fois dans un seul parcours (avant, testés isolément). Base du vrai frontend : `web/index.html`, HTML/CSS/JS vanilla (pas de framework, cohérent avec `vaultkey-saas-prototype.html` déjà dans le repo — reprend sa palette de couleurs/tokens CSS). `VAULT_ID = "demo-vault-1"` codé en dur en JS, pas de multi-coffre avant l'étape 7. Ce dossier est la vraie base pour les étapes 6 à 9, pas un spike jetable.

Correction de conception découverte à cette étape, dans `core/src/vault.rs` : `Vault::add_yubikey` générait le sel **en interne** à l'étape 1, ce qui est irréalisable en pratique — le sel doit être connu *avant* l'appel WebAuthn PRF (c'est un paramètre de l'appel, pas une sortie), alors que le secret PRF passé à `add_yubikey` est justement le résultat de cet appel. Nouvelle signature : `add_yubikey(credential_id, salt: &[u8;32], wrap_key: &[u8;32]) -> Result<(), VaultKeyError>`, le sel est maintenant fourni par l'appelant (généré en amont via `generate_salt()`, désormais exporté publiquement par `core/lib.rs`, et utilisé dans l'appel WebAuthn avant même d'atteindre `core/`). Ajout aussi de `Vault::list_files()`, absent jusqu'ici, nécessaire pour proposer un téléchargement sans connaître déjà le nom du fichier à l'avance. Ce genre d'erreur de séquencement est exactement ce que l'intégration bout-en-bout de cette étape est censée révéler, pas un oubli à se reprocher — les étapes 1 à 4 testaient chaque brique isolément, donc rien ne pouvait le détecter avant.

Nouvelle surface WASM (`wasm/src/lib.rs`), en plus de `demo_roundtrip` (conservé tel quel, toujours utilisé par `spikes/webauthn-prf-spike/`) : classe `WasmVault` qui expose le vrai `Vault` à JS (`create`, `fromEnvelopesJson`, `addYubikey`, `unlockWithYubikey`, `lock`, `addFile`, `readFile`, `listFilesJson`, `exportEncryptedManifest`), plus une fonction libre `generate_salt()`. `AddFileResult` : petit struct `#[wasm_bindgen]` à deux getters (`blob_id`, `ciphertext`) pour retourner deux valeurs — wasm-bindgen n'a pas de tuple JS natif, pattern à réutiliser si le besoin se represente.

Ajout non anticipé par le plan initial, découvert en branchant `web/` au serveur : **CORS**. La page statique et le serveur Docker tournent sur des origines différentes en développement (deux serveurs locaux distincts), et l'en-tête `Authorization` déclenche une préflight CORS que le serveur ne gérait pas. Ajout de `tower-http` (`cors`) avec `CorsLayer::permissive()` dans `server/src/main.rs` — permissif pour l'instant, à resserrer une fois qu'une vraie origine de déploiement existera (passe de durcissement, PRD §10), pas un relâchement définitif du modèle de sécurité.

Flux validé de bout en bout, avec de vrais contacts physiques YubiKey à chaque étape sensible (pas de simulation) : création du coffre (deux touches : enregistrement + dérivation PRF), upload d'un fichier réel, verrouillage (état JS entièrement vidé, pas juste `vault.lock()`), déverrouillage en relisant tout depuis le serveur avec un nouveau touch, téléchargement, fichier confirmé identique à l'original par l'utilisateur.

**Étape 6 (mode hors ligne, OPFS) : faite et validée le 2026-08-25, sur du vrai matériel, en coupant réellement le serveur (`docker compose stop`, pas une simulation navigateur).** Toujours dans `web/index.html`, toujours `demo-vault-1` codé en dur.

Vérification empirique préalable, à ne pas re-supposer : une doc MDN affirmait que Firefox ne supporte pas l'écriture OPFS (`createWritable()`) depuis le thread principal, seulement la lecture (recommandant un Web Worker + `createSyncAccessHandle`). **Faux sur la build de Zen/Firefox de cette machine** — testé directement dans la console avant de concevoir quoi que ce soit : l'écriture main-thread fonctionne. Pas de Web Worker ajouté, la doc était périmée sur ce point précis. À revérifier seulement si un autre navigateur pose vraiment problème, pas par précaution.

Trois décisions de conception, à ne pas rediscuter sans raison nouvelle :
- **Détection "hors ligne" sur l'échec réel d'un `fetch()`, jamais sur `navigator.onLine`.** `navigator.onLine` reflète l'état de l'interface réseau de l'OS, pas l'accessibilité du serveur VaultKey — couper le conteneur Docker (le moyen de test le plus fiable) ne le fait jamais basculer. Toute la logique de repli s'appuie sur des `try/catch` autour de `fetch`, jamais sur cet évènement.
- **Stratégie cache/réseau asymétrique selon la mutabilité de la donnée** : blobs de fichier = cache-first (immuables une fois créés, chaque upload produit un nouveau `blob_id`) ; `manifest.enc`/`envelopes.json` = réseau-first avec repli cache (évoluent dans le temps, la fraîcheur prime quand le réseau répond).
- **Resynchronisation** : bouton manuel "Synchroniser" + tentative automatique opportuniste juste après un déverrouillage réussi. Pas d'écoute passive des évènements `online`/`offline` du navigateur (peu fiable ici, voir le premier point).

Structure OPFS ajoutée, miroir de celle du serveur (PRD §5.1) : `vaults/demo-vault-1/{manifest.enc, envelopes.json, sync-state.json, blobs/<blob-id>.enc}`. `sync-state.json` (`{manifestPending, envelopesPending, pendingBlobIds}`) persiste l'état "en attente" à travers les rechargements de page — sans lui, un upload fait hors ligne perdrait sa trace au reload.

Cycle complet vérifié à la main, avec un vrai arrêt/relance du conteneur Docker (pas de simulation) : upload en ligne (badge "Synchronisé") → arrêt du serveur → upload d'un deuxième fichier hors ligne, réussi localement, badge "En attente" → **rechargement complet de la page, serveur toujours arrêté** → déverrouillage réussi depuis le seul cache OPFS (exigence PRD §6.2 confirmée noir sur blanc, pas supposée), les deux fichiers listés → relance du serveur → clic "Synchroniser" → le fichier passe à "Synchronisé" → confirmé aussi côté serveur (`docker compose exec vaultkey find /data`, le blob y est bien).

**Étape 7 (multi-coffre, gestion des YubiKey) : faite et validée le 2026-08-26, sur du vrai matériel, avec deux coffres réels créés depuis l'UI.** `web/index.html` a maintenant une sidebar (repris de `vaultkey-saas-prototype.html` : `.sidebar`, `.vault-item`, `.vault-nav`) — premier vrai rapprochement visuel avec la maquette. `currentVaultId` remplace la constante `VAULT_ID` codée en dur depuis l'étape 5.

Point du PRD §5.3 corrigé à cette étape, pas honoré avant : *"une seule cérémonie d'enregistrement WebAuthn par YubiKey suffit pour l'ensemble du drive"*. Jusqu'ici chaque création de coffre faisait un `navigator.credentials.create()` frais. Ajout d'un registre local `known-credentials.json` (racine OPFS, pas par coffre) : à la création d'un coffre ou à l'ajout d'une clé, l'utilisateur peut "réutiliser" une clé déjà connue (juste un `get()` + nouveau sel, pas de nouveau `create()`) ou en enregistrer une nouvelle. **Validé matériellement** : création du 2e coffre avec un seul contact YubiKey (touch de dérivation), aucune nouvelle invite d'enregistrement.

Serveur (`server/`) : deux routes de plus, même middleware d'auth et même style aveugle que le reste —
- `GET /vaults` : énumère les noms de sous-dossiers de `DATA_DIR/vaults/` (`Storage::list_vaults`), aucune lecture de contenu. Nécessaire pour qu'un nouvel appareil/navigateur découvre les coffres existants sans dépendre d'un index local par navigateur.
- `GET`/`PUT /vaults/{id}/meta` : nom lisible du coffre (`{name}`), dans un fichier séparé d'`envelopes.json` exprès — garde ce dernier fidèle au schéma exact du PRD §5.3 (matériel cryptographique uniquement), et le nom se synchronise entre appareils via le serveur (pas seulement local).

WASM (`wasm/src/lib.rs`) : ajout de `removeYubikey` à `WasmVault`, wrapper de `Vault::remove_yubikey` (existait dans `core/` depuis l'étape 1, jamais exposé à JS jusqu'ici).

Découverte des coffres au chargement (`discoverVaults()`) : `GET /vaults` fait autorité quand le réseau répond, repli entier sur l'index local `vaults-index.json` sinon (cohérent avec la logique réseau-d'abord/repli-cache de l'étape 6). Point à surveiller si ça devient gênant plus tard : les échecs réseau ET les échecs d'authentification (401, ex. jeton pas encore saisi) tombent tous les deux dans le même repli sur le cache local — pas distingué pour l'instant, accepté comme simplification (voir aussi la même simplification déjà notée pour `fetchWithCacheFallback` à l'étape 6).

Garde de retrait de YubiKey (PRD §6.4) : bouton "Retirer" désactivé (pas juste un refus silencieux) quand c'est la dernière clé du coffre — vérifié sur un coffre à 1 clé (désactivé) et à 2 clés (fonctionnel, repasse à 1). Le bouton RESET pour ce cas précis reste l'objet de l'étape 8, pas construit ici.

Décision de sauvegarde à la création : réduite à 2 options pour l'instant (2e YubiKey immédiate / acceptation explicite du risque) — la 3e option (BIP39) attend l'étape 8, pas de morceau d'UI à moitié câblé en attendant.

**Étape 8 (RESET, export/import, BIP39) : faite et validée le 2026-08-26, sur du vrai matériel.** `core/` avait déjà tout le nécessaire côté BIP39 depuis l'étape 1 (`Vault::enable_recovery_phrase`/`unlock_with_recovery_phrase`), jamais exposé à JS avant cette étape — deux méthodes de plus sur `WasmVault` (`enableRecoveryPhrase`, `unlockWithRecoveryPhrase`), wrappers directs.

**Bug réel trouvé et corrigé pendant le test de l'export**, pas juste en lisant le code : `toBase64()` utilisait `String.fromCharCode(...bytes)` (spread), qui dépasse la limite d'arguments du moteur JS au-delà de quelques dizaines de Ko — `RangeError: too many function arguments` dès qu'un blob/manifeste exporté dépassait cette taille. Corrigé par l'accumulation en chunks de 0x8000 octets (`String.fromCharCode.apply(null, bytes.subarray(...))`), pattern standard pour ce problème JS connu. Toutes les fonctions du fichier utilisant `toBase64` en profitent automatiquement (export, mais aussi l'encodage de `credentialId` qui n'était pas assez gros pour avoir jamais déclenché le bug).

**Correction de la garde de retrait de YubiKey posée à l'étape 7** : elle bloquait le retrait dès qu'il ne restait qu'une YubiKey, sans tenir compte de la phrase BIP39 (qui n'existait pas encore à l'étape 7). Condition corrigée dans `web/index.html` (`refreshYubikeyList`) : bloque seulement si `yubikeys.length === 1 && !recoveryPhrase.enabled`. Décisions de conception, côté serveur (`server/src/device_auth.rs`, nouveau module — remplace entièrement `server/src/auth.rs`, supprimé) :

Activé en mode **vendored** (compilé depuis les sources à l'intérieur du conteneur de build, `openssl = { features = ["vendored"] }` ajouté explicitement en dépendance directe) plutôt que de dépendre de la libssl du système — évite un couplage à la version exacte d'OpenSSL disponible dans l'image de base, au prix d'un temps de build plus long. À ne pas re-découvrir : si une future dépendance ajoute encore des paquets système au stage de build, revérifier que builder et runtime restent sur la même version de Debian, pas supposer que `bookworm-slim` convient par défaut.
- État en mémoire du processus, volontairement pas persisté sur disque : sessions actives (`HashMap<jeton, expiration>`, TTL 30 jours) et cérémonies de connexion en cours (`Option<PasskeyRegistration>`/`Option<PasskeyAuthentication>`, une seule à la fois — usage mono-opérateur, pas besoin d'une table par requête/cookie). Point de suppression : uniquement le bouton "Verrouiller" explicite (`delete unlockedVaults[currentVaultId]`) — cohérent avec le PRD §6.5, verrouiller doit rester un acte volontaire qui efface réellement la clé, changer de coffre ne doit plus jamais le faire à la place de l'utilisateur. Bénéfice secondaire : le point de statut par coffre dans la sidebar (ajouté dans la passe précédente) devient enfin réellement multi-coffre (`unlockedVaults[id]?.isUnlocked()` par coffre) au lieu de ne jamais pouvoir montrer qu'un seul point vert à la fois — il était correct mais artificiellement limité par l'ancienne contrainte, pas un bug de cette passe-là.

Décisions de conception, arbitrées avec l'utilisateur avant d'écrire quoi que ce soit :

- **Deux déclencheurs, deux jeux de tags** : push sur `main` → `:latest` + `:<sha complet, sans préfixe>` (traçabilité exacte même entre deux mises à jour de `:latest`) ; push d'un tag git `v*.*.*` → tag Docker identique verbatim (`type=ref,event=tag` dans `docker/metadata-action`, pas de reformatage semver) — pour épingler une version précise et figée sur le VPS quand `:latest` ne suffit pas.
- **Multi-arch (amd64 + arm64) via runners natifs en matrice, pas QEMU** : ce `Dockerfile` compile Rust en release avec OpenSSL vendored (`webauthn-rs`) + `wasm-pack`, déjà lent nativement — sous émulation QEMU ç'aurait facilement dépassé 45min-1h par build. Chaque job (`ubuntu-latest` pour amd64, `ubuntu-24.04-arm` pour arm64 — vérifié par recherche web que ce label est correct et gratuit pour un dépôt public, disponibilité GA depuis août 2025) pousse son image par digest, une job `merge` finale les assemble en un seul manifeste multi-arch sous les tags réels (pattern officiel `docker/build-push-action` pour builds multi-plateformes). Cache de build GitHub Actions (`type=gha`, scopé par plateforme) activé dès le départ, sans quoi chaque push recompilerait à froid.
- **`docker-compose.yml`** : `build: .` et `image: ghcr.io/drewing-eng/vaultkey:latest` coexistent sur le même service, pas deux fichiers séparés. `docker compose up --build` (dev local, testé après coup : reconstruit bien depuis les sources, ne tente aucun `pull`) inchangé ; `docker compose pull && docker compose up -d` (VPS) récupère l'image CI sans rien compiler sur la machine cible. Pour épingler une version précise plutôt que `:latest`, éditer directement ce tag dans le fichier.

Vérifié avant de considérer terminé : YAML du workflow et de `docker-compose.yml` tous deux valides (`python3 -c "import yaml..."`, `docker compose config`), `docker compose up -d --build` reconfirmé fonctionnel en local après le changement (aucune régression du flux de dev). **Le workflow lui-même n'a pas encore tourné** (pas encore poussé sur GitHub au moment de l'écriture de cette note) : premier run, visibilité réelle du package, et le manifeste multi-arch résultant restent à confirmer une fois poussé.

**Reste avant mise en ligne publique** : déploiement VPS proprement dit (choix de la machine pas encore fait, `RP_ID`/`RP_ORIGIN`, TLS/reverse proxy en amont — sujet Caddy remis à zéro, voir plus haut, à relancer par l'utilisateur quand il le souhaite —, fenêtre de bootstrap du premier appareil à respecter).

## Manière de travailler établie dans ce projet

- Toute commande nécessitant un mot de passe interactif (sudo, notamment) doit être **exécutée par l'utilisateur lui-même** dans son propre terminal, jamais scriptée à l'aveugle. Lui donner la commande exacte à copier-coller.
- Avant toute action destructive (suppression de fichiers, de dépendances installées, reset de données), lister précisément ce qui va être touché et demander confirmation explicite avant d'exécuter. Ne rien supprimer silencieusement, même si ça semble évident.
- Vérifier empiriquement (documentation à jour, comportement observé sur la machine) plutôt que supposer, en particulier pour tout ce qui touche au support navigateur de WebAuthn/PRF : le projet s'est déjà fait surprendre une fois par une hypothèse non vérifiée sur les entitlements Apple (FSKit), à ne pas reproduire côté navigateurs.
- Tout artefact secondaire généré pendant le développement (clés de test, exports temporaires, fichiers de scratch) va dans le répertoire scratchpad de la session, pas à la racine du projet.
